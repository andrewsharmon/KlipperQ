# Klipper host and Mainsail over USB/ADB

- Date: 2026-09-26 UTC
- Board: Arduino UNO Q 2 GB; device-specific USB serial intentionally omitted
- Result: **PASS for Klippy/Moonraker/Mainsail access over a local ADB forward**
- Browser URL: `http://127.0.0.1:8181/`

## Installed software

- Klippy source: the host portions of the same local `uno-q` checkout used for MCU development, version `v0.13.0-770-gce7002bed-dirty`
- Moonraker source commit: `1cfb0c41e468645951a371621f06d32777b6107c`
- Mainsail: `v2.19.0`
- nginx: Debian 1.26.3
- Python: 3.13.5

The board had no working network interface. A temporary localhost HTTP/HTTPS proxy was carried through `adb reverse` to install signed Debian packages and pinned Python dependencies. The proxy process and reverse tunnel were removed after installation.

The board clock was corrected from 2025-06-25 to the host's current UTC time before TLS downloads. Required Debian packages upgraded some stock userspace libraries; `needrestart` reported several service restarts deferred, including NetworkManager and the desktop session. No reboot was performed.

## Klippy result

Klippy runs as user `arduino`, with `dialout` supplementary access to `/dev/ttyHS1`. Its service conflicts with the stock Arduino UART services and resets MCU execution through Arduino's installed OpenOCD reset helper before connection. The reset performs no flash write.

The initial host attempt used Klipper's default 250000 baud and timed out. Adding the firmware's verified `baud: 115200` produced a successful unmodified Klippy connection:

- MCU version loaded successfully
- MCU type `stm32u585xx`
- Clock estimate approximately 159.9 MHz against the declared 160 MHz
- Configuration completed with 1,024 moves
- Observed serial statistics had zero invalid frames

The minimal configuration uses `kinematics: none` and defines no external outputs.

## Web result

Moonraker connected to Klippy and reported `klippy_state: ready` with no failed components. Mainsail's root page returned HTTP 200 through the Mac-side forward `tcp:8181 -> tcp:80`. The forwarded `/server/info` endpoint reported `klippy_connected=true`, and `/printer/info` reported `Printer is ready`.

The first nginx rule proxied `/websocket/` but not Moonraker's exact `/websocket` endpoint, so the static UI loaded while Mainsail displayed `Cannot connect to Moonraker`. The route was corrected and an RFC 6455 upgrade through `127.0.0.1:8181` returned HTTP `101 Switching Protocols`. HTTP API checks continued to report Klippy ready after the fix.

Moonraker listens on board loopback `127.0.0.1:7125`; nginx listens on board loopback `127.0.0.1:80`. No web listener is exposed on a board network interface.

The initial slim Klipper host copy omitted `config/` and `docs/`, producing two file-manager warnings. Those directories were copied from the matching checkout. Moonraker initially requested PolicyKit permissions for systemd and host reboot/power actions. An unprivileged `provider: none` configuration cleared the warnings but removed those functions; the user explicitly rejected that tradeoff. The official Moonraker PolicyKit rules and `moonraker-admin` supplementary group were therefore installed, and the `systemd_dbus` provider was restored. This enables approved service management and host reboot/shutdown actions from Moonraker while clearing the PolicyKit warnings.

The first full-stack restart test exposed a board-specific reset behavior: `/opt/openocd/bin/arduino-reset.sh` left the STM32 executing from system ROM (`PC 0x0bf...`), so Klippy owned `/dev/ttyHS1` but timed out waiting for `identify_response`. A reset-halt followed by loading the stack and reset-handler values from the application's vector table at `0x08000000` started the existing image without rewriting flash. The dependency-free UART probe then passed identify, `get_config`, and two `get_clock` requests at 160 MHz and 115200 baud. The deployed Klipper unit now uses `host/klipperq-start-mcu.sh`, which validates both vectors before starting the application.

During UI testing an explicit `emergency_stop` webhooks request placed the no-output configuration into shutdown. The log showed `Shutdown due to webhooks request` with otherwise clean serial statistics. Restarting the Klippy service reset MCU execution through the no-write OpenOCD reset helper and returned the printer to ready.
